## Changes since v0.9.8

- Serialize user deactivation and deletion with API token issuance, and roll
  token creation back if its audit event cannot be committed. This preserves
  account policy across browser and API paths under concurrent requests.
- Repair staging PoP gateway reporting by carrying an inspected literal host
  gateway address into generated agent Compose configuration. The host-specific
  DNS and logging overrides remain part of the staging installation.
- Add bounded TLS maintenance recovery, domain deletion authorization checks,
  WAF and compression runtime propagation, edge-cell reconciliation, and
  operational log limits. The exact changes and their tests are in the linked
  comparison and [handoff evidence](../development-handoff.md).

There is no new application, PowerDNS or ClickHouse migration relative to the
previous staged source `4cd61eeee8e2252575db377e5ca722f53a492d50`.
Upgrades from older releases still require every intervening explicit migration
and the ordering in the [upgrade guide](../../deployment/upgrade.md).

## Staging result and limits

The release was deployed to one control node and two IPv4 DNS/edge PoPs.
Running CDNFoundry image references matched all applicable verified manifest
digests. Control health/readiness and Grafana health passed; both PoPs answered
authoritative UDP/TCP SOA and served the expected disposable resource over
verified HTTPS. Both edges reported ready gateways/listeners and eight cells.
The PostgreSQL snapshot catalog was verified and named volumes were unchanged.
See the [staging rollout record](../development-handoff.md).

The owner-run [browser checklist](https://github.com/vaheed/CDNFoundry/blob/main/docs/manual-browser-qualification.md) remains
open. There is no live production deployment, and the full Phase 9 load,
failure, recovery, external IPv6 and owner-evidence matrix has not passed.
Therefore `v0.9.9` is **staging-qualified, not production-accepted**.

## Run the CDN

1. Start with the [production quick start](../../deployment/production-quick-start.md):
   prepare the three hosts, independent management DNS, owned platform and
   disposable customer zones, origin, registrar access and approved IP families.
2. Check out this exact commit. Download the successful run's release evidence;
   verify the signed manifest and all 17 image digests, then project them into
   Fleet. Preserve existing PostgreSQL, volumes, keys, PKI and TLS material.
3. Validate generated bundles, activate control and explicit migrations, then
   each DNS/edge PoP in order. Use the documented browser or API onboarding
   path to register DNS clusters, platform identity, edges, pools and domains.
4. Execute the [production qualification](../production-qualification.md),
   including external DNS/TLS, traffic, failure and recovery measurements and
   the owner browser checklist. Record every unavailable requirement as open.

Do not point customer production traffic at the fleet until that qualification
report and its release decision pass.
