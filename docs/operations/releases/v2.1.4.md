# CDNFoundry v2.1.4

v2.1.4 adds request and response rules, Linux host preparation in Fleet, and backup verification history.
It also changes runtime resource use and expands the operator and domain-owner documentation.

## Request and response rules

- The domain panel's **Rules** tab and API support redirects, URL rewrites, request and response headers, and cache rules.
  Each type has its own ordered table and presets. See the [guide](../../guides/request-rules.md) and
  [reference](../../reference/request-rules.md) for supported conditions, actions, and limits.
- Rules run after security decisions. Blocked or challenged requests cannot be redirected or rewritten into an allow.
  Origin selection and protected headers remain constrained.
- Rule changes publish asynchronously to assigned cells. Invalid bundles retain the active generation, and edge revision
  rollback restores request rules atomically. Access logs record rules that acted.
- Existing cache path rules migrate into cache rules, preserving order and matching behavior.

## Fleet and operations

- Fleet prepares supported Linux hosts and preserves resolver access when activating authoritative DNS.
- Backup history shows recent snapshots and verification status. Failed database exports are rejected, and backup
  completion requires a verified receipt. See [backup and recovery](../backup-and-recovery.md).
- Edge cell CPU and memory limits are configurable with `EDGE_CELL_CPUS` and `EDGE_CELL_MEMORY`.
  The [hardware guide](../hardware-requirements.md) includes sizing measurements and a calculator that checks the
  busiest domain against its cell.

## Runtime and fixes

- PHP and nginx images are updated. Production control containers build Laravel and Filament caches at startup.
- Cells use jemalloc, parse inline WAF rules once, skip inline ModSecurity when WAF is off, and skip CRS response rules
  in the scoring listener.
- Cell access logs are buffered and sent to Vector. ClickHouse health checks use HTTP, high-volume system logs are
  disabled, and remaining system logs have bounded retention.
- Queue lanes with only delayed or reserved jobs report zero waiting age.
- Rule tabs switch on one click, phone actions remain visible, and documentation diagrams support both themes.

## Upgrade notes

1. Back up PostgreSQL, application encryption and signing keys, and externally stored TLS material before upgrading.
2. Deploy the signed, digest-pinned release through Fleet using the [upgrade guide](../../deployment/upgrade.md).
   This release includes two database migrations: creation of `request_rules`, then additional rule types and conversion
   of existing cache path rules. Do not run old control-plane writers against the migrated cache settings.
3. Update edge agents, gateways, and cells together with the control plane so they understand request rule bundles.
   Restart cells to load runtime and allocator changes. Retain the previous valid generation during activation.
4. Verify DNS, HTTPS, rule publication, cache behavior, and backup verification on your fleet before admitting traffic.

Database rollback refuses to remove rewrite, header, or cache rules while they exist. An edge revision rollback restores
runtime desired state; it does not reverse the database migration. Plan database recovery from the pre-upgrade backup
instead of assuming a binary downgrade reverses migrated cache settings.

## Qualification status

This is release preparation, not a completed production qualification. The
[request rules qualification record](../request-rules-qualification-2026-11-21.md) records automated and IPv4/IPv6
runtime evidence, with complete browser, visual, and accessibility qualification still open. The

The separate multi-PoP WAF staging gate remains open. A passing preparation check does not close those gates.
